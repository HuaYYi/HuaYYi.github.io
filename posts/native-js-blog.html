零框架博客是怎么炼成的：Self Static Blog 架构笔记

这个博客没有用 React、Vue，甚至没有用 jQuery——全部是原生 HTML、CSS、JavaScript。这不是为了怀旧，而是一次认真权衡后的选择。这篇文章把整个架构摊开讲讲：为什么这么做、怎么做的、踩过哪些坑。

为什么不用框架

先看需求：一个首页（搜索框 + 网址导航 + 文章列表）、归档页、关于页、文章详情页。页面总数不到 10 个，交互以「渲染 JSON 数据」为主，没有复杂的状态流转。

框架解决的核心问题是「状态与视图的同步」。当页面上有大量动态状态互相影响时，框架的声明式渲染能救命；但当你的状态少到可以用几个全局变量说清楚时，引入框架带来的是构建链、依赖升级、概念负担，收益却很小。对于部署在 GitHub Pages、希望「克隆下来就能跑」的静态博客，零依赖就是最大的功能。

JSON 驱动：内容与代码分离

整站的可变内容全部抽成了 JSON 文件，改配置不需要碰任何 JS。站点配置留在根目录，其余数据统一收在 data/：

  • site-config.json：站名、主题色、背景动画参数、本地模式开关
  • data/search-engines.json：首页大搜索框的引擎列表
  • data/nav-links.json：网址导航的分类与链接
  • data/quotes.json：随机名言
  • data/posts-list.json：文章元数据（标题、日期、摘要、分类）

页面脚本的启动流程是统一的：common.js 读完站点配置，注入主题色 CSS 变量、渲染头部页脚，然后广播一个 ssb-config-ready 事件，各页面自己的 initPage(config) 再接管剩下的渲染。这样每个页面脚本只关心自己的板块，公共逻辑收敛在一处。

数据存哪里：本地与线上双轨

静态站没有数据库，数据怎么存？答案是双轨：

  • 本地模式：文章元数据和正文直接存进浏览器的 localStorage（列表一个键、正文每个文件一个键），不访问网络、不需要任何令牌，适合离线写作和预览；
  • 线上模式：通过 GitHub Contents API 把文章以 commit 的形式提交到仓库，仓库再触发 Actions 构建发布。

两种模式下，读文章的代码是同一套：getPosts() 先拉仓库里的 data/posts-list.json，本地模式再并入 localStorage 里的文章。对前台来说，文章来自 GitHub 还是来自浏览器，没有任何区别。

构建与部署

开发版代码带大量注释、保持可读；上线前由 build.mjs 压缩进 dist/：HTML 去注释折叠空白、CSS 用 clean-css、JS 用 terser。唯一原样拷贝的是 posts/*.html——文章正文不做任何转换，保证读到的和仓库里存的是同一份字节。

踩过的坑

  • flex 子元素默认 min-width: auto，内容一宽就把容器撑爆，横向溢出——记得显式设 min-width: 0；
  • scrollIntoView({ inline: 'center' }) 在窄屏上会把整页拖走，手动算 scrollLeft 反而稳；
  • JS 要读 CSS 变量时，必须在「定义它的那个元素」上 getComputedStyle，读到 :root 头上可能是空。

没有框架，「组件化」怎么办

原生 JS 里同样可以有组件思维，关键是划清边界。这个项目的做法是：一个板块 = 一个渲染函数 + 一份数据 + 一段作用域 CSS。比如网址导航：数据来自 data/nav-links.json，渲染只发生在 #nav-zone 内部，类名统一以 nav- 开头防冲突。函数执行完，DOM 已就位，事件委托挂在容器上，没有虚拟 DOM、没有 diff，但「数据变了就重渲染这块」的效果是一样的。

状态管理也极简：当前 tab、当前页码、当前搜索引擎，各用一个模块内变量保存，翻页函数是唯一的修改入口。状态少、入口唯一，就不需要库来帮你追踪变化。

性能与体积：白手起家的红利

整站前端 JS 加起来不到几十 KB，没有运行时、没有 hydration，HTML 下载完即可交互。首屏的主要「负担」反而是浏览器自己的渲染——这也是为什么动画坚持用 canvas + requestAnimationFrame 而不是狂堆 DOM：六个飘浮圆用一个全屏 canvas 统一绘制，比六个绝对定位的 div 各自触发合成层要省。

零依赖还带来一个隐性收益：供应链为零。没有 node_modules 就没有「每周一百个安全公告」，三年后打开仓库，node scripts/serve.mjs 依然能跑，不存在框架大版本升级导致的搁浅。

什么时候我会反过来选框架

如果未来出现这些信号，就该重新评估：页面需要大量实时联动状态（编辑器协同、仪表盘）；团队多人协作需要强约束的组件契约；需要 SSR/ISR 等服务端能力；或者交互复杂到手写渲染的代码量开始失控。技术选型是对当前约束的回答，不必从一而终。

框架是工具不是信仰。需求简单时，原生技术栈 + 良好的代码组织，完全可以撑起一个干净、可维护、跑得飞快的站点。
